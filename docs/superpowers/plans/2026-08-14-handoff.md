## THE BLOCKER — Task 2 decision gate

The committed `gan_linear` kernel is correct but **~49× slower than the cuBLAS
floor**, which makes it unusable as written.

Measured on tig-gpu (RTX 4060), chunk 65536, under a valid GPU claim:

| n | current Gaussian gen | cuBLAS floor | **this kernel** | µs/1k |
|---|---|---|---|---|
| 707,000 | ~120 ms | 462 ms | **22,515 ms** | 31.8 |
| 909,000 | ~155 ms | 610 ms | **29,091 ms** | 32.0 |
| 1,111,000 | ~189 ms | 759 ms | **35,658 ms** | 32.1 |
| 1,313,000 | ~223 ms | 904 ms | **42,163 ms** | 32.1 |
| 1,515,000 | ~258 ms | 1,045 ms | **48,551 ms** | 32.0 |

Dead flat at ~32 µs per 1,000 vectors across the whole active track range —
the n-sweep is complete and unambiguous. At the largest track the kernel would
add **48.5 seconds** to both `tig-runtime` and `tig-verifier`, against a current
total runtime of ~1 second.

The chunk sweep (16384 / 65536 / 262144 at n=1,515,000) was still running as
background task `blcsrjo44`, monitor `bjuvjuags`. Expect chunk size to make
almost no difference: it changes buffer sizes, not the per-row weight re-read
that dominates. If it *does* move the number materially, the diagnosis below is
wrong and should be re-examined.

**Diagnosis, quantitative.** The kernel uses one CUDA block per input row, so
each block reads all four layers' weights — 7.08 MB — for a single vector.

- 707,000 × 7.08 MB = **5.00 TB** of weight traffic
- 5.00 TB / 22.515 s = **222 GB/s**; at 909k it is **221 GB/s**

The 4060's DRAM bandwidth is ~272 GB/s, so the kernel is running at ~81% of
peak bandwidth. It is not badly written for what it does — the *approach* is
wrong.

**The fix.** A tiled variant: each block computes `BM × BN` outputs with input
rows *and* weight tiles staged in shared memory. `BM = 64` cuts weight traffic
64× (5.00 TB → 78 GB), making the kernel compute-bound at ~2.5 TFLOP, i.e.
around the cuBLAS floor.

Determinism survives tiling: the requirement is a fixed accumulation order over
`k` *per output element*, and tiling changes which block owns an element, not
the order within it. Keep `BM`/`BN`/`BK` compile-time constants. **Do not use
split-K** — partitioning `k` across blocks and reducing afterwards reintroduces
exactly the order-dependence being avoided.

**A second, independent problem.** Even at the cuBLAS floor the GAN forward
pass is ~462 ms against the current generator's ~120 ms — about **4×**, in both
`tig-runtime` and `tig-verifier`, so it roughly doubles verification cost
network-wide. That is inherent to 1,769,472 MACs per vector and no kernel work
removes it. Only a smaller (distilled) generator would.

**Both questions were put to the user and are unanswered.** They interrupted
before answering. Do not proceed past the gate on your own judgement — ask.

### GPU work MUST hold a claim

`reaper.kill_orphan_cuda` computes `exempt = set(protect) | own_pids()`, and
`own_pids()` reads the claim records. A bare `./bench` holds no claim and gets
**SIGKILLed** — this destroyed five benchmark runs before it was understood.
Anything run under `gpu-claim` is exempt.

The queue is not on `PATH`; source at `/workspace/gpu-queue-management`:

```bash
export QUEUE_ROOT=/workspace/queue GPU_CLAIM_DIR=/workspace/lock/gpu \
       GPUQ_CONFIG=/workspace/gpuq.toml
/venv/main/bin/python -m gpuqueue.cli_gpuq list          # queue state
/venv/main/bin/python -m gpuqueue.cli_claim --status     # live claims
/venv/main/bin/python -m gpuqueue.cli_claim --vram-mb 3072 --wait -- <cmd>
```

Capacity: 8188 total − 512 default reserve = **7676 MiB usable**;
`gpu_max_jobs` defaults to **2 holders**. A claim with `vram_mb: null` means
*the whole card* and `ledger.fits:232` then refuses every co-tenant.

**A live claim was amended.** The user's training job
(`wgan-synthetic-20260814T081702Z-306165`) was submitted without `--vram-mb`,

## Corrections to things previously believed

- The blob is **7,088,684 bytes**, not 7,088,652. The plan's original figure
  omitted the 32 bytes of per-layer `(in_dim, out_dim)` pairs. Fixed in
  `03007c08`. sha256
  `883ff17c808ec31c408232093778708e4119ec3e5329255703288b2e41a497f8`.
- **GPU contention was negligible, not significant.** An earlier benchmark
  reading was dismissed as "contended and untrustworthy" (29,102.5 ms at 909k);
  the clean re-run gave 29,091.1 ms — a 0.04% difference. Both are valid.
- The production algorithms do **not** blindly hardcode 250 dims. Both
  `autovector_g` and `there_v10` declare `const DIMS: usize = 250` and
  explicitly guard `if challenge.vector_dims as usize != DIMS { return Err(...) }`.
  The SIGSEGV observed at 128 dims is most likely that error crossing the dylib
  boundary between a locally-built runtime and the officially-compiled `.so`,
  not the guard itself. The per-algorithm fix is ~20–40 lines (two constants in
  `mod.rs`, four `250` literals in 672 lines of `kernels.cu`).
- Both algorithms also hardcode the track sizes
  (`match num_queries { 7_000 | 9_000 | 11_000 | 13_000 | 15_000 => ... }`),
  so the ecosystem assumes challenge parameters are frozen.
