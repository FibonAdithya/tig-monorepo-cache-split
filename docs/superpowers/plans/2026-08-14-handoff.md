## What was decided, and why

**Task 2 gate.** The first kernel used one block per input row and re-read all
7.08 MB of weights per vector — 5.00 TB of traffic, 22,515 ms at 707k vectors,
~49x the cuBLAS floor and bandwidth-bound at ~81% of the 4060's 272 GB/s. The
shipped kernel tiles a 128x64 output block with an 8x4 per-thread register
tile: 628 ms at 707k and 1,335 ms at 1,515k, inside 1.5x of the floor.
Determinism survives because tiling changes which block owns an output element,
not the accumulation order within it. **Split-K must never be used** — it
partitions `k` across blocks and reduces afterwards, reintroducing exactly the
order-dependence being avoided.

The residual ~5x cost against the old generator's ~120–250 ms is inherent to
1,769,472 MACs per vector and was accepted. Only a smaller generator removes it.

**Task 6 calibration.** `QUALITY_OFFSET = 1.616563`, `QUALITY_SCALE = 6.399004`,
fitted across all five tracks from 24 nonces each. Worst residual 282 quality
units (at n_queries=11000); every other track within 138.

The user chose to match the per-track band and accept ~7–9x wider per-nonce
variance, over compressing the scale or going per-track. The reasoning and the
three rejected mitigations are in the spec's risk section. **The key fact to not
re-derive:** `quality = (offset - avg_dist)/scale` is linear, so one constant
fixes both the cross-track drift and the per-nonce noise, and their ratio
(12.3 for GAN vs ~73 on mainnet) is a property of the data. No choice of
constants changes it.

## Corrections to things previously believed

- **The Task 2 "second, independent problem" is resolved, not open.** It read as

- **Exact 1-NN is admissible.** An earlier note in this file's lineage implied
  brute force blows the fuel budget. It does not: `fuel_consumed` is 3.84e11 at
  n_queries=7000, scaling to ~1.76e12 at 15000, against `max_fuel_budget` 5e12.
  The confusion was between the `--fuel` *ceiling* passed on the command line
  (1e14) and actual consumption. Only `test_algorithm`'s 1e11 default was too
  small.
- **The plan's Task 5 Step 7 no longer works as written.** It says to change
  `block_size` from 256 to 128, but the tiled kernel's `block_dim` is `(16,16)`,
  fixed by the tile constants. It also compares the quality integer, which is
  ~10^5 too coarse to detect a last-bit change. Replaced with FNV-1a digests
  over the raw device buffers across four forward-chunk/latent-block
  combinations, plus a negative control. See the spec.
- **The plan's ~100-unit residual criterion for "fixed constants suffice" is the
  wrong test here.** It assumes quality is near-deterministic per nonce, as it
  is on mainnet. With per-nonce sigma ~500, a 282-unit residual in the mean is
  not the binding constraint, so per-track constants would fix the smaller
  problem. Do not "fix" the residual without re-reading this.
- The blob is **7,088,684 bytes**, sha256
  `883ff17c808ec31c408232093778708e4119ec3e5329255703288b2e41a497f8`.
- The production algorithms do not blindly hardcode 250 dims — `autovector_g`
  and `there_v10` both declare `const DIMS: usize = 250` and guard on it. They
  also hardcode the track sizes, so the ecosystem assumes challenge parameters
  are frozen. Only 2 of ~92 algorithms were ever tested against the dimension
  change; do not generalise from them.

### The determinism argument, now checked statically

`build_ptx` compiles with **`-arch compute_70 -code sm_70`** — the shipped
artifact is architecture-neutral PTX that each host driver JITs locally. So the
arithmetic can be audited from the emitted PTX without any GPU. Compiling
`tig-challenges/src/vector_search/kernels.cu` with those exact flags and
counting float ops per kernel:

| kernel | exact ops | inexact (SFU) ops |
|---|---|---|
| `gan_linear` | 96 `fma.rn.ftz.f32`, 32 `mul.ftz.f32`, 32 `setp.ge.ftz.f32` | **none** |
| `gan_sample_latents` | 8 `fma.rn`, 16 `mul` | 4 each of `sin.approx`, `cos.approx`, `lg2.approx`, `sqrt.approx` |
| `evaluate_total_distance` | 7 `fma.rn`, 2 `add`, 7 `sub` | 2 `sqrt.approx` |

**`gan_linear` — the only kernel this project introduced — is provably clean.**
Its source comment claims "only fmaf/mul/add/select appear here"; the emitted
PTX now confirms it. That claim is no longer just an assertion.

The approximate ops in the other two are **inherited, not introduced**, and that
matters for the risk assessment:

- `evaluate_total_distance` is **byte-identical** to `3efbdec9`'s version (the
  diff is a trailing newline).
- `curand_normal` and `sqrtf` already appear in the base's `generate_clusters`,
  so Box-Muller transcendentals are in the *current mainnet* generation path.

Since the live challenge verifies successfully today across a heterogeneous GPU
fleet, those SFU ops are empirically bit-stable on the architectures actually in
use. **State this as the inference it is:** the base challenge feeds *different*
values into those ops (Gaussian mixture, not GAN outputs), and SFU bit-stability
is in principle input-dependent, so this is strong evidence rather than proof.
But the risk is inherited from a working production system, not created here.

Net effect on open item 1: the cross-architecture concern is now narrowed from
"the whole generator is unverified off sm_89" to "two inherited kernels rely on
SFU bit-stability that mainnet already exercises." The new code is clean by
static audit.

**The workaround that makes measurement possible without `build_so`.** You do
not need an instrumented `.so` to measure anything. `build_ptx` works fine (it
only needs `nvcc`), and the algorithm PTX contains *both* the challenge's
`gan_*` kernels and the algorithm's own. So a scratch binary can:

1. `CudaContext::new(0)`, `ctx.load_module(Ptx::from_file(<algo>.ptx))`
2. `settings.calc_seed(&rand_hash, nonce)` — `BenchmarkSettings` is
   `{player_id, block_id, challenge_id, algorithm_id, track_id}`, and
   `challenge_id` is `"c004"`
3. `Challenge::generate_instance(&seed, &track, module, stream, &prop)`
4. launch the solver kernel, then `challenge.evaluate_solution(...)` for the
   quality integer (it is `pub` unless the `hide_verification` feature is on)

This bypasses `tig-runtime`, the `.so`, LLVM, and the fuel machinery entirely.
It is the only way validation got done on this box. **Delete such bins after
use** — they need the `vector_search`/`cuda` features and otherwise break
`cargo test --workspace`.

**A confound worth knowing before planning any cross-architecture test.**
`calc_seed` hashes the jsonified settings, *including `track_id`*. So changing
the track encoding changes every instance. The sm_86 digests measured on
2026-08-25 are therefore not comparable with the earlier sm_89 ones — the
architecture change and the `n_queries=7000` → `s=sift_128` change landed
together. Any real cross-architecture check must hold `track_id` fixed.
